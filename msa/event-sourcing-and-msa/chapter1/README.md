# 도메인 주도 설계
모델은 단순하게 표현한 실제 세계다. 모델을 표현할 때는 해결 해야 하는 문제를 바라보는 다양한 관심사 중 하나를 선택해서 문제를 설명하는데 꼭 필요한 것만 선택 해야 함. 그렇지 않으면 모델이 여러 관심사를 담아 한 없이 복잡해지게 된다. 관심사에 따라 문제를 정의하는 모델이 달라져야 한다. 자신이 관심 있는 속성만 보는 것이 모델의 응집도를 높이고 모델관 결합도를 낮추는 방향이다.

## 1.1 도메인 로직 패턴
소프트웨어에서 도메인 로직을 어디에 두는지는 마틴 파울러에 의해 크게 4가지로 분류된다. 트랜잭션 스크립트 패턴, 테이블 모듈 패턴, 서비스 레이어 패턴, 도메인 모델 패턴에 대해 알아보자.

### 1.1.1 트랜잭션 스크립트 패턴
클라이언트가 요청한 비즈니스 로직을 하나의 프로시저가 모두 처리함. 비즈니스 애플리케이션이 제공하는 기능들을 반복적인 CRUD로 처리할 수 있을 떄 적합함. 서블릿과 JSP를 이용하는 것이 대표적인 사례다.

### 1.1.2 테이블 모듈 패턴
테이블 모듈은 데이터베이스 테이블 단위로 비즈니스 로직을 처리하는 것을 분리하는 패턴이다. DAO를 사용한다고 보면 된다.

### 1.1.3 서비스 레이어 패턴
서비스 레이어 패턴은 독립된 레이어에 시스템 통합과 전체 흐름을 조정하는 책임을 가진다. Controller-Service-Dao로 요청할 때의 Service와 동일시 해도 무관하다.

### 1.1.4 도메인 모델 패턴
도메인 모델 패턴은 데이터와 행위를 하나의 객체로 설계한다. 다양한 규칙과 논리의 복잡한 관계를 여러 도메인 객체에 분산히키고 객체간 협력으로 구현함.
